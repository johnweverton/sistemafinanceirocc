# Story 7.1 — Fundação multi-conta: migration, tipos, registro de contas e env

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** que o domínio conheça o conceito de "conta emissora" (MC / Cavalcante Viana) em
médicos, boletos e configuração de ambiente,
**so that** as camadas de gateway e UI possam emitir, cancelar e conciliar boletos pela
empresa correta sem quebrar nada do que funciona hoje pela MC.

## Contexto
O sistema assume uma única conta Cora global (env `CORA_*`). A empresa opera com duas contas
(MC configurada; Cavalcante Viana pendente). Decisões D1/D2/D3 aprovadas pelo dono (2026-07-10)
em `docs/architecture/feature-multi-conta-emissora.md`: conta é atributo do médico (D1-A),
credenciais em env prefixadas por conta com registro estático (D2-A), webhook com secret por
conta e reconsulta pela conta do boleto (D3).

Esta story é a fundação: schema + tipos + env + repositórios. Não muda comportamento em
runtime — o gateway continua mono-conta até a 7.2.

## Acceptance Criteria
1. **Migration `0021_conta_emissora.sql` (@data-engineer):** aditiva e idempotente:
   - `medicos.conta_emissora text not null default 'mc'` + CHECK `in ('mc','cavalcante_viana')`;
   - `boletos.conta_emissora text not null default 'mc'` + mesmo CHECK (desnormalização
     proposital — boleto guarda a conta que o emitiu, ver arquitetura §3);
   - `vw_recebiveis` recriada (`create or replace`) expondo `b.conta_emissora`;
   - comentários de coluna + rollback comentado no rodapé (padrão das migrations).
2. **Tipos shared (`packages/shared`):** `ContaEmissora = 'mc' | 'cavalcante_viana'`;
   `Medico.contaEmissora` e `Boleto.contaEmissora` no domínio; Zod schemas atualizados.
3. **Registro de contas:** `apps/web/src/server/gateway/contas-emissoras.ts` (novo) com
   `CONTAS_EMISSORAS` (slug, `nomeExibicao`, `envPrefix`) conforme arquitetura §2-D2.
   Nada de credencial no registro — só metadados.
4. **Env multi-conta (`lib/env.ts`):** vars `CORA_MC_*` e `CORA_CV_*` (CERT_BASE64, KEY_BASE64,
   API_URL, CLIENT_ID, WEBHOOK_SECRET — todas opcionais no schema) + helper
   `getCredenciaisConta(conta)` que resolve prefixo → credenciais com **fallback das `CORA_*`
   legadas para `mc`**. Conta sem credenciais → erro nomeando a conta e as vars faltantes.
5. **Repositórios/mappers:** `medico-repository`, `boleto-repository` e recebíveis leem/gravam
   `conta_emissora`; `criarBoleto` aceita o campo (a rota só passa a usá-lo na 7.2).
6. **Regressão zero:** com apenas as env legadas configuradas, toda a suíte existente passa
   sem alteração de comportamento (backfill `'mc'` + fallback garantem o baseline).
7. `npm run typecheck`, `lint` e `test` verdes.

## Complexidade e Riscos
- **Complexidade:** S (~2 pontos). Tudo aditivo; sem mudança de comportamento.
- **Escopo OUT:** uso da conta no gateway/rotas (7.2); UI (7.3); credenciais reais da CV
  (gate externo — assinatura Cora Pro da CV pendente de decisão de custo do dono).
- **Riscos:** fallback legado mal resolvido quebraria a MC em produção — *mitigação:* AC 6 é
  bloqueante; teste dedicado do `getCredenciaisConta('mc')` só com `CORA_*` legadas.
- **DoD:** AC 1–7 + File List completa.

### Decisões de implementação
- `getCredenciaisConta` mora em `env.ts` (único leitor de `process.env`, Coding Standard);
  o registro `contas-emissoras.ts` guarda só metadados (slug/nomeExibicao/envPrefix).
- Insert de `conta_emissora` em `criarBoleto` é CONDICIONAL (só quando o param vem):
  produção pré-migration continua funcionando; pós-migration o default 'mc' cobre a omissão.
- Mappers usam o padrão `modo_cobranca` (0018): coluna opcional na Row + `?? 'mc'` no toX —
  banco sem a migration não quebra leitura.
- `webhookSecret` no retorno de `getCredenciaisConta` é nullable e NÃO entra na validação de
  faltantes — secret de webhook ausente não pode bloquear emissão (consumo real na 7.2).
