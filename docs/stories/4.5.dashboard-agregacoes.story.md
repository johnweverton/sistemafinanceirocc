# Story 4.5 — Agregações do Dashboard financeiro (RPC/views)

## Status
Ready

## Story
**As a** gestor do escritório,
**I want** funções/visões de agregação financeira (por competência, por médico e aging de vencidos),
**so that** o dashboard (4.6) leia KPIs prontos sem cálculo pesado no cliente.

## Acceptance Criteria
1. Agregação **por competência**: total emitido, recebido, em aberto, vencido e **taxa de
   inadimplência** (RPC `rpc_dashboard_por_competencia` ou view).
2. Agregação **por médico**: mesmos totais + ticket médio.
3. **Aging** de vencidos em faixas: 0–30, 31–60, 60+ dias (com base em `vencimento`).
4. Repositório tipado em `shared` (`ResumoCompetencia`, `ResumoMedico`, `AgingFaixa`) + funções de
   leitura no backend.
5. `typecheck`, `lint`, `test` verdes.

## Complexidade e Riscos
- **Complexidade:** M (~3 pontos). Concentra-se em SQL (RPC/views) + tipos + leitura.
- **Escopo OUT:** a UI do dashboard (4.6).
- **Riscos:** correção das agregações (reusar a MESMA regra de status derivado da 4.4 para não
  divergir). *Mitigação:* centralizar a regra numa view base reutilizada pelas agregações.
- **DoD:** AC 1-5 + testes verdes + File List completa.

## Dev Notes
**Depende de 4.4** (modelo de recebíveis / status derivado).

- **Consistência é crítica:** a taxa de inadimplência e os totais devem usar a mesma definição de
  status derivado da 4.4. Preferir uma **view base** (ex.: `vw_recebiveis`) e agregar em cima dela,
  para não duplicar a regra em dois lugares.
- Aging só considera boletos vencidos e sem baixa; faixas por `current_date - vencimento`.
- Delegar o SQL ao @data-engineer; o dev integra tipos + leitura + rota.
