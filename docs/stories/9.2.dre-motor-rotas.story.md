# Story 9.2 — Motor de categorização + relatório do DRE + rotas

## Status
Ready

## Story
**As a** equipe financeiro,
**I want** que o extrato sincronizado se categorize sozinho na maior parte dos casos (com
uma fila pequena para revisão manual) e que eu consiga cadastrar despesas fora da Cora e
ver o resultado do período,
**so that** o DRE saia praticamente pronto do dia a dia, sem trabalho de categorização
linha a linha.

## Contexto
Fundação pronta na 9.1 (schema + repositories puros, sem motor/rotas). Esta story
implementa o D3 (motor de categorização) e o D4 (relatório com expansão de recorrência em
leitura, sem cron) da arquitetura, mais todas as rotas HTTP do épico — cadastro de plano
de contas, regras, ação de categorizar, lançamentos manuais e o relatório.

**Decisão de escopo (@sm, além da tabela literal da arquitetura §7):** as 2 auto-regras
de sistema (D3) só cumprem a promessa de "a fila fica pequena sozinha" se rodarem no
MOMENTO DO SYNC, não só quando alguém chama a rota de categorizar uma-a-uma. Por isso o
AC 2 estende `POST /api/extrato/sincronizar` (rota já em produção desde a 8.2) para
rodar o motor de categorização logo após o matching de conciliação — mesma sequência,
mesmo espírito. É uma extensão aditiva (nunca sobrescreve categoria já confirmada
manualmente) e cai dentro do "motor" que já era escopo desta story.

## Acceptance Criteria
1. **Engine `categorizacao.ts` (função pura, sem I/O, mesmo padrão de `conciliacao.ts`):**
   recebe transações (shape mínimo: tipo, transactionType, contraparteNome, descricao,
   flag `conciliadaComBoleto`) + regras ativas ordenadas por prioridade + os 2 ids de
   categoria de sistema, devolve para cada transação `{ categoriaId, status }`:
   - `CREDIT` já conciliado com boleto (Épico 8) → categoria *Receita de honorários*,
     `confirmada` (dedução lógica de um fato já confirmado, não uma sugestão);
   - `DEBIT` com `transactionType='FEE'` → categoria *Tarifas bancárias*, `confirmada`;
   - senão, primeira regra ativa cujo `padrao` aparece (substring, case-insensitive) no
     campo indicado (`contraparte_nome` ou `descricao`) → categoria da regra, **sempre**
     `sugerida` (nunca confirma sozinha, ao contrário das 2 regras acima);
   - nenhuma bateu → `sem_categoria`.
2. **`POST /api/extrato/sincronizar` (8.2, estendido):** após aplicar as transições de
   conciliação, busca **todas** as transações da conta com `status_categorizacao =
   'sem_categoria'` (filtro da AC 8 — não só o lote deste sync; resolve de brinde
   qualquer transação antiga que nunca foi categorizada) e roda `categorizacao.ts` sobre
   elas; nunca recategoriza o que já é `sugerida`/`confirmada` (não sobrescreve decisão
   prévia, manual ou automática) e persiste via `categorizarTransacao` (9.1). Resposta do
   sync ganha `categorizacao: { confirmadas, sugeridas, semCategoria }` no resumo.
3. **Rotas de plano de contas** (`GET/POST /api/plano-contas`, `PATCH/DELETE
   /api/plano-contas/[id]`): leitura admin/financeiro; escrita **admin** (mesmo padrão
   `config-cobranca`). POST valida `grupo` (whitelist Zod) + `nome`; PATCH só aceita
   `nome`/`ordem` (nunca `grupo`/`sistema` — nem no schema Zod, reforçando o repository);
   DELETE mapeia `CATEGORIA_SISTEMA_PROTEGIDA`/`CATEGORIA_INATIVA`/`CATEGORIA_EM_USO` do
   repository para os status certos (400/400/409).
4. **Rotas de regras** (`GET/POST /api/plano-contas/regras`, `PATCH/DELETE
   /api/plano-contas/regras/[id]`): admin (mesmo padrão do item 3). POST valida
   `categoriaId` (UUID), `campo` (whitelist), `padrao` (string não vazia). **A 9.1 só
   criou `desativarRegra` (soft-disable) — esta story acrescenta `excluirRegra` (DELETE
   físico) ao `plano-contas-repository.ts`.** Regra é cadastro-folha (nenhuma outra
   tabela referencia `plano_contas_regras.id`), então o DELETE físico não precisa do
   guard de vínculos que `excluirCategoria` tem.
5. **`POST /api/extrato/[id]/categorizar`** (admin/financeiro, rate limit 30/min — mesmo
   padrão de `/conciliar`): body opcional `{ categoriaId }` — presente = correção/
   confirmação manual (`status='confirmada'`, sempre aceito, mesmo sobre uma sugestão ou
   `sem_categoria`); ausente = roda o motor para ESSA transação isolada (útil para
   recategorizar sob demanda, ex. depois de cadastrar uma regra nova). Transação
   inexistente → 404.
6. **Rotas de lançamentos manuais** (`GET/POST /api/dre/lancamentos`, `DELETE
   /api/dre/lancamentos/[id]`): admin/financeiro. POST valida o corpo com Zod (schema
   discriminado por `tipoLancamento`, espelhando o CHECK cruzado da migration 0023) antes
   de chegar no repository — dupla validação (Zod na borda + repository), igual ao padrão
   dos outros formulários do projeto.
7. **Engine `relatorio-dre.ts` (função pura, D4) + `GET /api/dre/relatorio`**
   (admin/financeiro, query `inicio`/`fim`/`conta?` — `conta` ausente = consolidado
   MC+CV): agrega `extrato_transacoes` categorizadas + `dre_lancamentos_manuais` do
   período por categoria/grupo; lançamento **recorrente é expandido em instâncias
   mensais NA LEITURA** (uma instância por mês na interseção `[dataInicio, dataFim ??
   hoje] ∩ [inicio,fim]` do relatório) — **sem cron, sem materializar linha nenhuma**.
   Resposta: total por categoria, subtotal por grupo, `resultadoLiquido = receitas −
   deducoes − despesasOperacionais − despesasFinanceiras`.
8. `extrato-repository.ts` (`listarTransacoes`) ganha filtro opcional
   `statusCategorizacao` (mesmo padrão dos filtros existentes) — preparação para a fila
   de categorização da 9.3.
9. `npm run typecheck`, `lint` e `test` verdes; suíte existente do Épico 8/9.1 sem
   regressão (o AC 2 toca a rota de sync já em produção — o teste existente de
   `sincronizar.test.ts` continua passando, mais os casos novos).

## Complexidade e Riscos
- **Complexidade:** L (~5 pontos) — maior que o normal do épico: 2 engines puros + 8
  rotas + extensão de uma rota já em produção. Escopo mais largo que 9.1/8.2, mas cada
  peça é isolada e testável separadamente.
- **Escopo OUT:** UI (9.3); exceção por mês em recorrência; recategorização retroativa em
  massa (a regra nova só se aplica ao que ainda está `sem_categoria` a partir de então);
  gráficos/comparativo entre períodos.
- **Riscos:**
  - Estender a rota de sync (8.2, produção) quebrar o comportamento existente —
    *mitigação:* AC 9 exige o teste pré-existente de `sincronizar.test.ts` verde sem
    alteração de asserções; categorização é aditiva e só toca `sem_categoria`.
  - Recategorização em sync duplicar trabalho a cada re-sync — *mitigação:* filtro
    explícito por `status_categorizacao='sem_categoria'` antes de rodar o motor (AC 2).
  - Expansão de recorrência com bug de borda de mês (fevereiro, `dataFim` no meio do
    período) — *mitigação:* bateria de testes do engine cobrindo início/fim de janela,
    `dataFim` null vs preenchido, mês parcial nas duas pontas.
  - Zod duplicando a validação do repository (AC 6) parecer redundante — *mitigação:*
    é o padrão já usado no projeto (borda + domínio); mantém a rota com erro 400 limpo
    mesmo se o repository um dia mudar.
- **DoD:** AC 1–9 + File List completa.

## Dev Notes
- Padrões a seguir: `conciliacao.ts` (engine puro table-driven), rotas de `/extrato/[id]/*`
  (rate limiter 30/min, `withErrorHandler<{id:string}>`, Zod na borda), `config-cobranca`
  (admin-only em escrita de cadastro).
- `relatorio-dre.ts` recebe dados JÁ categorizados/filtrados pelo repository (sem I/O) —
  mesma separação leitura-de-banco/lógica-pura do `conciliacao.ts`.
- `dre-repository.ts` (9.1) ganha a função de agregação que chama `relatorio-dre.ts`
  (fetch bruto + delega o cálculo ao engine).
- **Localizar as 2 categorias de sistema por `sistema=true` + `grupo`, NUNCA por `nome`**
  — `atualizarCategoria` (9.1) permite renomear qualquer categoria, inclusive as de
  sistema (só bloqueia mudar `grupo`/`sistema`); dentro de cada grupo só existe 1 linha
  `sistema=true`, então a busca é `listarCategorias().find(c => c.sistema && c.grupo ===
  'receita')` (e análogo para `deducao_receita`) — nunca `find(c => c.nome === '...')`.

## Testing
Vitest. Chaves: motor de categorização (as 2 auto-regras nunca cedem a uma regra de
usuário conflitante — auto-regra sempre vence por vir antes no fluxo; regra de usuário
nunca confirma sozinha), sync não recategoriza o que já tem categoria, CRUD de plano de
contas/regras com os guards do 9.1 refletidos na rota (403/400/409 corretos), categorizar
manual sobrescreve sugestão, expansão de recorrência (mês parcial nas duas pontas,
`dataFim` null, fevereiro), resultado líquido calculado corretamente com receita+dedução+
despesas operacionais+financeiras.
