# Story 10.8 — Fix cobrança dupla de pediatra com via de acesso + recálculo de resultado

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** que o motor conte corretamente as guias de pediatra com procedimentos de via de
acesso, e que eu consiga corrigir um resultado já gravado sem recriar a execução inteira,
**so that** a cobrança reflita a produção real (regra 3x1) e um dado corrigido na origem depois
da execução não fique travado no valor antigo.

## Contexto
Reportado pelo dono (2026-08-04, screenshot do relatório): o Dr. José Neias Araújo Ribeiro
(pediatra) apareceu com "38 GUIAS · 38 CIRURGIAS · CONSOLIDADO 17" — o valor correto, confirmado
pelo dono, era 19 guias (ele é 3x1). O sistema estava cobrando praticamente o dobro do correto.

Investigação encontrou DUAS causas independentes, ambas corrigidas nesta story:

1. **`isPediatra()` não reconhecia a especialidade truncada.** No cadastro, a especialidade do
   Dr. José Neias está gravada como `"Pediatr"` (sem o "a" final). A função exigia a substring
   completa `"pediatra"` ou `"pediatria"` — `"Pediatr"` não batia em nenhuma das duas, então o
   médico NUNCA entrava no ramo pediatra do motor (nem na contagem 3x1, nem na regra de via de
   acesso por paciente). GATE do dono (2026-08-04): variações/truncamentos como esse ainda
   significam pediatra — `isPediatra()` passou a reconhecer o PREFIXO `"pediatr"`.
2. **Mesmo com `isPediatra()` corrigido, a contagem de via de acesso de pediatra agrupava pela
   senha da origem (`atendimentoExternoId`), não pelo paciente.** A origem (Sistema Web) atribui
   uma senha PRÓPRIA a cada procedimento de via de acesso, mesmo dentro do mesmo atendimento —
   ex.: 3 cirurgias do mesmo paciente no mesmo dia, 3 senhas diferentes. Agrupar por senha
   fragmentava um único atendimento 3x1-elegível em várias guias, ignorando a regra por completo.
   Corrigido para agrupar por `(pacienteNome, data)`, mesma regra 3x1 dos itens normais.

Sem os dois fixes juntos, o resultado do Dr. José Neias continuaria em 38 guias (fix 1 sozinho
não muda nada, porque o motor ainda contaria 1 guia por senha dentro do ramo pediatra; fix 2
sozinho nunca seria aplicado, porque o médico nunca entrava no ramo pediatra).

Adicionalmente, o dono apontou (mesma mensagem) que quando o dado de origem é corrigido DEPOIS
que uma execução já rodou, não havia nenhuma forma de atualizar o resultado gravado sem criar
uma execução inteira nova. Confirmado via GATE (AskUserQuestion, 2026-08-04): implementar agora,
junto com o fix do 3x1.

## GATE de negócio — respondida (2026-08-04, @dono)
1. **Escopo do fix de contagem:** aplicar para TODO pediatra com via de acesso (não só o caso
   relatado) — "Sim, pra todo pediatra com via de acesso (recomendado)".
2. **Recálculo:** implementar agora, junto com o fix do 3x1 — "Sim, implementar agora junto com
   o fix do 3x1".
3. **Tolerância de `isPediatra()`:** "ele é pediatra, o sistema tem que reconhecer esses tipos
   como pediatra, se faltar um A, não muda muita coisa que o entendimento é que ele é pediatra."

## Acceptance Criteria
1. `isPediatra()` reconhece o prefixo `"pediatr"` (case-insensitive), não exige a palavra
   completa — cobre truncamentos/variações como `"Pediatr"`, `"Pediatra Neonatal"` etc.
2. `contarGuiasProducao()`: para pediatra, itens `viaAcesso` são agrupados por
   `(pacienteNome, data)` com `Math.ceil(count/3)` por balde — mesma regra 3x1 dos itens normais.
   Comportamento de não-pediatra (1 guia por `chaveAtendimento`/senha) preservado.
3. `consolidarProducao()`: mesmo ajuste para o número informativo "consolidado" (agrupa por
   `pacienteNome`, ignorando data, mesmo padrão já usado pelos itens normais desta função).
4. Réplica do caso real (17 pacientes, 15 com ≤3 itens via de acesso + 2 com 4 itens cada,
   cada item com senha própria) → 19 guias, não 38.
5. **Recálculo:** endpoint `POST /api/execucoes/resultados/[id]/recalcular` reprocessa a MESMA
   linha de `execucao_resultados` com os itens de produção ATUAIS da origem (reaproveita
   `processarMedico`, mesma seleção de produção já gravada na execução original).
6. Recálculo bloqueado (409 `BOLETO_JA_EMITIDO`) se já existir boleto ativo (emitido/pago) para o
   resultado — evita divergência silenciosa entre o boleto já emitido e o valor gravado.
7. Recálculo só é suportado para resultado de MÉDICO (422 `RECALCULO_NAO_SUPORTADO` para
   resultado agregado de empresa/cliente contábil, que não têm produção individual).
8. Botão "Recalcular" na UI (`RelatorioGrupos.tsx`), nos grupos "Prontos para emissão" e
   "Requerem revisão", visível só quando o resultado tem `medicoId` e ainda não tem boleto
   emitido.
9. `npm run typecheck`, `lint`, `test` verdes.

## Complexidade e Riscos
- **Complexidade:** M (~5 pontos) — 2 causas raízes no Engine (achado real, sem GATE prévio;
  investigação + GATE feitas na mesma sessão) + endpoint novo de recálculo com orquestração de
  I/O própria (reaproveita o Engine puro, mas busca dados de fontes diferentes de uma execução
  nova) + migration + UI.
- **Escopo OUT:**
  - Não recalcula automaticamente nada — é uma ação explícita do operador, por resultado.
  - Não corrige `isPediatra()` para variações com acento (`"Cirurgia Pediátrica"` não bate no
    prefixo ascii `"pediatr"`) — fora do escopo relatado (truncamento, não acentuação); registrado
    como limitação conhecida no teste unitário de `isPediatra`.
  - Não migra dados históricos automaticamente — resultados antigos com o bug (José Neias e
    quaisquer outros pediatras com via de acesso >3 itens/paciente) precisam de um "Recalcular"
    manual por resultado, ou de uma execução nova.
- **Riscos:** mudança em função central (`isPediatra`, usada por 6 arquivos) — mitigado por rodar
  a suíte completa (841 testes) após a mudança, sem nenhuma regressão.

## Dev Notes
- **Por que duas causas raízes e não uma:** a investigação inicial (contagem por senha em vez de
  paciente) já explicava por que via de acesso ficaria fragmentado, mas rodar o cálculo com o fix
  isolado contra o dado real do Dr. José Neias devolveu 38, não 19 — sinal de que o ramo pediatra
  nem estava sendo executado. Comparar a especialidade real gravada (`"Pediatr"`) contra
  `isPediatra()` confirmou a segunda causa. Sem essa verificação teria sido fácil declarar o fix
  "pronto" com um teste que na verdade não reproduzia o bug relatado (o teste de ouro inicial
  usava `'Pediatra'` completo, que sempre passou — só falhou ao trocar para `'Pediatr'`, o valor
  real do banco).
- **`recalcularResultado` reaproveita a seleção original**, não uma nova escolhida pelo operador:
  busca `execucao_selecoes` pela `execucaoId` do resultado + `medicoId`, e chama `buscarItens` de
  novo para essa mesma `producaoExternaId` — os itens vêm atualizados porque a ORIGEM foi
  corrigida, não porque o operador escolheu uma produção diferente.
- **Por que limpar `status_original`/`revisado_*` no recálculo:** esses campos registram uma
  revisão manual do cálculo ANTIGO (agora obsoleto); manter uma "revisão" apontando para um
  status que não existe mais confundiria a auditoria. O próprio recálculo já tem seu rastro
  (`recalculado_por`/`recalculado_em`).
- **Dados históricos:** o Dr. José Neias e resultados parecidos (mesmo padrão de alerta
  "procedimento(s) sem código ou descrição") precisam de "Recalcular" manual — fora do escopo
  desta story automatizar isso; ver Change Log para o que foi corrigido manualmente após o deploy.
