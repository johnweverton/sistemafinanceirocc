# Story 13.5 — Fase 2: disparo pelo sistema web (solicitações) e agente agendado

## Status
Ready for Review

## Story
**As a** operador do escritório contábil que já usa o diálogo de lote para lançar o faturamento dos
clientes em `faixa_faturamento`,
**I want** clicar em um botão "Buscar no ISS" dentro do próprio sistema (em vez de pedir para
alguém rodar o agente no terminal) e ver o progresso da busca,
**so that** eu não dependa de outra pessoa estar na máquina do escritório com o agente instalado
para conseguir os valores do ISS.

## Contexto
Épico 13, Fase 2. Depende das Stories 13.1 (rotas/tabelas do agente), 13.3 (propostas no diálogo de
lote) e 13.4 (Fase 1 — UI de 3 estados, modo assistente). A Fase 1 simplificou o uso *do agente*; esta
story tira o gatilho do terminal: o operador pede a busca pelo sistema web, uma solicitação fica
registrada no banco, e o agente — rodando sozinho na máquina do escritório, vigiando ou agendado —
a executa e relata o progresso de volta. A senha do ISS **continua só local** (decisão G4, preservada
— nada de credencial na Vercel). O que muda é só *quem aciona* e *como o progresso aparece*.

## Acceptance Criteria

### Migration `0062_iss_solicitacoes.sql` (item a)
1. Nova tabela `iss_solicitacoes`: `id uuid pk`, `competencia text` (mesmo formato/CHECK `^\d{4}-(0[1-9]|1[0-2])$` das tabelas da 0061), `documentos text[]` nullable (`null` = carteira inteira de
   `faixa_faturamento`; preenchido = só aquele(s) CPF/CNPJ, para "Tentar de novo" de uma empresa),
   `status text` com `CHECK` em `('pendente','em_andamento','concluida','falhou','cancelada')`,
   `solicitado_por uuid not null references profiles(id)` (mesmo padrão de `criado_por` em
   `lotes_emissao`, migration 0038), `solicitado_em timestamptz not null default now()`,
   `iniciado_em timestamptz`, `finalizado_em timestamptz`, `progresso_atual integer`,
   `progresso_total integer`, `execucao_id uuid references iss_execucoes_agente(id)` (a execução
   registrada pela rota já existente, quando a solicitação termina com sucesso), `mensagem_erro text`,
   `maquina text`, `heartbeat_em timestamptz`.
2. Índice único parcial `uq_iss_solicitacoes_competencia_ativa on iss_solicitacoes (competencia) where
   status in ('pendente','em_andamento')` — barreira real no banco contra duas solicitações ativas
   na mesma competência ao mesmo tempo (mesmo padrão de `uq_boletos_resultado_ativo`, migration 0037:
   índice único parcial faz a corrida morrer no Postgres, não em código). Vale mesmo para uma
   solicitação de "tentar de novo" de uma empresa só: só pode haver UMA ativa por competência,
   documentos ou não.
3. Índices de apoio: `(competencia, solicitado_em desc)` e um parcial em `status = 'pendente'` (apoio
   à consulta de "próxima solicitação" do agente).
4. RLS coerente com a 0061: `enable row level security` + policy de leitura para os mesmos papéis das
   rotas de faturamento de clientes contábeis (`admin`, `colaborador`, `financeiro` — os mesmos de
   `requireRole` em `propostas-iss/route.ts`); sem policy de escrita para clientes — grava só via
   service role, nas rotas novas (mesmo padrão da 0038/0061).
5. Migração aditiva/idempotente (`create table if not exists`, `drop constraint if exists` +
   `add constraint`, índices `if not exists`) com bloco de ROLLBACK comentado no fim, no mesmo
   formato da 0061. **Aplicação manual no Supabase pelo dono** (mesmo processo da 0061).

### Tipos e rotas do usuário (item b)
6. Novo tipo `SolicitacaoIss` (e `StatusSolicitacaoIss`) em `packages/shared/src/types/agente-iss.ts`
   (mesmo arquivo dos tipos do Épico 13), espelhando as colunas da tabela em camelCase.
7. `POST /api/clientes-contabilidade/faturamentos/iss-solicitacoes` (sessão normal, `requireRole(['admin','colaborador','financeiro'])` —
   mesma guarda de `propostas-iss/route.ts`): body `{ competencia: 'AAAA-MM', documentos?: string[] }`.
   Cria a solicitação com `status = 'pendente'` e `solicitado_por = userId` da sessão. **Idempotente**:
   se já existe uma ativa (`pendente`/`em_andamento`) para a competência, devolve ELA (200), sem criar
   duplicata — o índice único parcial (AC 2) é a barreira de verdade; o código trata a violação (Postgres
   `23505`) recuperando a linha existente, mesmo espírito de "reserva antes de chamar" da 0037.
8. `GET /api/clientes-contabilidade/faturamentos/iss-solicitacoes?competencia=AAAA-MM` (mesma guarda):
   devolve a solicitação ATIVA da competência, ou — se não houver — a mais recente de qualquer status
   (para a UI mostrar "concluída às 10:42" mesmo depois de terminar), ou `null`.
9. `POST /api/clientes-contabilidade/faturamentos/iss-solicitacoes/[id]/cancelar` (mesma guarda):
   marca `status = 'cancelada'` só se estiver `pendente` ou `em_andamento`; qualquer outro status ⇒
   422 (nada a cancelar).

### Rotas do agente (item c)
10. `GET /api/integracoes/iss/solicitacoes/proxima` (bearer `AGENTE_ISS_TOKEN`, mesma guarda
    `requireAgenteIssToken` das rotas da 13.1): reivindica ATOMICAMENTE a solicitação a processar —
    a `pendente` mais antiga (`solicitado_em asc`) OU, se não houver nenhuma pendente, uma
    `em_andamento` cujo `heartbeat_em` está há mais de 10 minutos sem atualizar (agente anterior
    caiu no meio) — marca `status = 'em_andamento'`, `heartbeat_em = now()`, `maquina` (do corpo/host
    informado) e `iniciado_em` (se ainda `null`). Sem nenhuma candidata: `204 No Content`.
11. `POST /api/integracoes/iss/solicitacoes/[id]/progresso` (mesma guarda): body
    `{ atual: number, total: number }`; exige a solicitação estar `em_andamento` (senão 409); grava
    `progresso_atual`, `progresso_total`, `heartbeat_em = now()`.
12. `POST /api/integracoes/iss/solicitacoes/[id]/concluir` (mesma guarda): body
    `{ execucaoId: string } | { erro: string }` (union — sucesso XOR falha, mesmo espírito das
    capturas com `status`/`mensagemErro` da 13.1). Sucesso ⇒ `status = 'concluida'`,
    `execucao_id`, `finalizado_em = now()`. Falha ⇒ `status = 'falhou'`, `mensagem_erro`,
    `finalizado_em = now()`. Exige a solicitação estar `em_andamento` (senão 409).
13. `POST /api/integracoes/iss/execucoes` (rota já existente, 13.1) ganha um campo opcional
    `solicitacaoId` no corpo — adicionado a `novaExecucaoIssSchema`
    (`apps/web/src/server/validation/agente-iss-schema.ts`) e ao tipo `NovaExecucaoIss`
    (`packages/shared/src/types/agente-iss.ts`). Quando presente, `registrarExecucaoIss`
    (`apps/web/src/server/repositories/iss-captura-repository.ts`) valida que existe uma
    `iss_solicitacoes` com esse id e `status = 'em_andamento'` (422 se não) — é uma GUARDA de
    consistência; **quem efetivamente conclui a solicitação continua sendo o `POST .../concluir`
    (AC 12)**, chamado pelo agente logo depois deste envio, para não duplicar a máquina de estados
    em dois lugares.

### Agente: modo vigiar / execução agendada (item d)
14. O miolo de uma execução (hoje dentro de `main()` em `apps/agente-iss/src/cli.ts`: buscar alvos,
    logar, iterar empresas, salvar parcial, montar o relatório) é extraído para uma função reutilizável
    `executarCompetencia({ competencia, documentos, onProgresso })` que devolve o mesmo formato de
    `NovaExecucaoIss` hoje montado por `montarExecucao` — usada tanto pelo fluxo de linha de comando
    de hoje (13.2/13.4) quanto pelo novo modo vigiar, SEM duplicar a lógica de login/troca de
    inscrição/extração.
15. Novo modo `--vigiar` (`npm run iss:faturamento -- --vigiar`): a cada 60s, chama
    `GET /solicitacoes/proxima`; ao receber uma, roda `executarCompetencia` com a `competencia` e os
    `documentos` da solicitação (documentos preenchidos = só aquelas empresas, mesmo filtro que
    `--cnpj` já faz hoje em `cli.ts`), chamando `POST /solicitacoes/{id}/progresso` a cada empresa
    (via `onProgresso`) e, ao final, `POST /execucoes` (com `solicitacaoId`) seguido de
    `POST /solicitacoes/{id}/concluir`. Falha de login (`ErroLogin`) ou qualquer erro que impeça
    produzir uma execução chama `concluir` com `{ erro: mensagem }` em vez de deixar a solicitação
    presa em `em_andamento`.
16. Novo modo `--uma-vez`: faz UMA consulta a `/solicitacoes/proxima` e, se houver, processa e
    termina (sem laço de 60s) — pensado para ser chamado pelo Agendador de Tarefas do Windows a cada
    minuto, como alternativa ao `--vigiar` de processo contínuo.
17. `scripts/agente-iss/instalar-tarefa-agendada.cmd` (novo): registra, via `schtasks`, uma tarefa que
    roda `npm run iss:faturamento -- --uma-vez` a cada minuto; documentado (comentários no próprio
    `.cmd` + seção no README) como alternativa ao `--vigiar`.
18. Senha do ISS continua só em `%USERPROFILE%\agente-iss\.env` (G4 preservada) — nenhuma rota nova
    recebe ou expõe `ISS_SENHA`. A sessão do portal é reaberta (login) uma vez por solicitação
    processada (mesmo padrão de hoje: um `browser`/`PortalIss` por rodada de `executarCompetencia`),
    não mantida entre solicitações diferentes.

### UI no `LoteContabilidadeDialog` (item e)
19. Novo componente `apps/web/src/components/clientes-contabilidade/SolicitacaoIssPainel.tsx` (mesmo
    padrão de separação de `PropostaIss.tsx`: peça de apresentação por cima de lógica pura testável)
    com o botão "Buscar no ISS", desabilitado com o motivo em `title`/texto quando já existe uma
    solicitação ativa para a competência (AC 7); ao lado, quando ativa, o indicador
    "Buscando no ISS… 34/90" a partir de `progresso_atual`/`progresso_total`.
20. Nova consulta `clienteContabilidadeQueryKeys.solicitacaoIss(competencia)` /
    `clientesContabilidadeService.solicitacaoIss(competencia)` (`apps/web/src/services/clientes-contabilidade.ts`)
    com `refetchInterval` que faz o polling a cada ~5s SÓ enquanto `status` é `pendente`/`em_andamento`
    (mesmo padrão já usado em `useExecucaoRealtime.ts` e `LoteEmissaoDialog.tsx`:
    `refetchInterval: (q) => ativa(q.state.data) ? 5000 : false`), parando sozinho ao concluir/falhar/cancelar.
21. Cada tick do polling (e a conclusão) invalida `clienteContabilidadeQueryKeys.propostasIss(competencia)`
    — a mesma query que `LoteContabilidadeDialog.tsx` já usa (`propostasQ`, linha ~167) e que já é
    revalidada manualmente após um lançamento (linha ~284). Como o estado local `faturamentos` só
    guarda o que o OPERADOR digitou (`valorDoCampo` cai em `valorInicialDoCampo(estadoIssPorCliente(...))`
    quando o campo não foi tocado — confirmado em `LoteContabilidadeDialog.tsx:182-184`), os campos
    que ele não mexeu se preenchem sozinhos conforme o agente avança, sem sobrescrever o que ele já
    digitou.
22. Aviso "o computador do escritório com o agente parece desligado" quando a solicitação está
    `pendente` há mais de 3 minutos (comparando `solicitadoEm`) ou `em_andamento` com `heartbeatEm`
    parado há mais de 3 minutos — função pura testável `agentePareceDesligado(solicitacao, agora)`
    em novo `apps/web/src/lib/solicitacao-iss.ts` (mesmo estilo de `apps/web/src/lib/proposta-iss.ts`).
23. Botão "Tentar de novo" por empresa no estado "Digite à mão" (cinza — Story 13.4) por
    `nao_encontrado`/`erro`: cria uma solicitação com `documentos: [pagadorDocumento]` só daquele
    cliente (campo já usado em `listarAlvosIss`, `apps/web/src/server/repositories/iss-captura-repository.ts:42`,
    exposto no cadastro via `c.cobranca?.pagadorDocumento`).
24. Botão "Cancelar" na solicitação ativa, chamando o `POST .../cancelar` (AC 9); desaparece quando
    não há solicitação ativa.

### Fora de escopo (item f)
25. Execução agendada automática mensal (sem gatilho humano) e "Dar Ciência" (G2) continuam
    explicitamente fora desta story.

## Dev Notes
- **Migration de referência para o índice único parcial (AC 2):** `supabase/migrations/0037_idempotencia_boletos.sql`
  cria `uq_boletos_resultado_ativo` com `where status in (...)` — mesma técnica aqui, com
  `competencia` em vez de `execucao_resultado_id`. É a barreira REAL; o código da rota só trata a
  violação (23505) de forma amigável (AC 7).
- **Migration de referência para a tabela/colunas de auditoria (AC 1, 4):** `supabase/migrations/0038_lotes_emissao.sql`
  (`lotes_emissao`) tem o mesmo desenho — `criado_por uuid not null references profiles(id)`,
  `status text check (...)`, `progresso integer`, RLS de leitura só para papéis específicos, escrita
  só via service role. `iss_solicitacoes` segue o mesmo molde, com `solicitado_por` no lugar de
  `criado_por`.
- **Reivindicação atômica (AC 10) — achado de código:** o repositório NÃO usa hoje nenhuma função
  Postgres (`rpc`) nem `SELECT ... FOR UPDATE SKIP LOCKED` em lugar nenhum (verificado por busca em
  `supabase/migrations` e `apps/web/src/server`); o padrão existente para corrida é sempre um índice
  único parcial (0037) ou, na emissão em lote (0038), aceitar a corrida residual e deixar o próximo
  processamento pular o item já tratado. `[AUTO-DECISION] Como reivindicar a próxima solicitação →
  SELECT da candidata (pendente mais antiga, ou em_andamento com heartbeat velho) seguido de UPDATE
  condicional (.eq('id', id).eq('status', statusLido)); 0 linhas afetadas = perdeu a corrida, devolve
  204 (o agente tenta de novo no próximo ciclo de 60s) (reason: só existe UM agente-iss rodando por
  vez na prática — G4, CLI local de uma máquina do escritório — então o custo de uma corrida perdida
  é só esperar 60s a mais, e criar uma função Postgres nova introduziria um padrão sem precedente no
  projeto para um risco que hoje é teórico)`.
- **`solicitacaoId` no payload de `/execucoes` (AC 13) — decisão de desenho:** a máquina de estados
  da solicitação (quem marca `concluida`/`falhou`) fica inteiramente em `POST .../concluir` (AC 12);
  o campo em `/execucoes` é só uma GUARDA de consistência (a execução realmente correspondia a uma
  solicitação `em_andamento`), para não duplicar a lógica de conclusão em duas rotas. `iss_solicitacoes.execucao_id`
  (não uma coluna nova em `iss_execucoes_agente`) é o único lugar que guarda o vínculo — evita
  referência cruzada nos dois sentidos.
- `registrarExecucaoIss` hoje (`apps/web/src/server/repositories/iss-captura-repository.ts:114-173`)
  já segue o padrão "valida tudo antes de gravar, 422 se algo não bate" (`validarClientes`) — a
  checagem do `solicitacaoId` (AC 13) entra no mesmo lugar, antes do primeiro `insert`.
- **Extração do miolo do CLI (AC 14):** hoje o laço de captura por empresa vive dentro de `main()`
  em `apps/agente-iss/src/cli.ts:143-188` (login, loop `for (const [i, alvo] of alvos.entries())`,
  `salvar()` parcial a cada empresa). `executarCompetencia` deve devolver o mesmo formato que
  `montarExecucao` (`apps/agente-iss/src/relatorio.ts`) produz hoje, para que tanto `cli.ts` (fluxo
  de hoje) quanto `vigiar.ts` (novo) montem o `NovaExecucaoIss` do mesmo jeito.
- **Progresso "N/total" já existe como log** (`diag.log` em `cli.ts:144`, formato "(${i+1}/${alvos.length})") —
  o `onProgresso` de `executarCompetencia` é o mesmo gancho, só que também chamando
  `POST /solicitacoes/{id}/progresso` quando vier do modo vigiar (no modo CLI comum, `onProgresso`
  simplesmente não bate em rede nova, só loga como hoje).
- **Polling — precedente exato a seguir:** `apps/web/src/hooks/useExecucaoRealtime.ts:20` e
  `apps/web/src/components/execucoes/LoteEmissaoDialog.tsx:111` já usam
  `refetchInterval: (q) => condição ? Nms : false` — a nova query de `solicitacaoIss` deve seguir a
  MESMA forma, não inventar outro mecanismo de polling.
- **`faturamentos` só guarda o que o operador digitou (AC 21) — já é assim hoje**, confirmado em
  `LoteContabilidadeDialog.tsx:181-184` (`valorDoCampo`): não é preciso mudar essa função, só
  garantir que o polling novo invalide `propostasIss` (mesma invalidação já feita em `onSuccess` do
  `lancarFaturamentos`, linha 284).
- `pagadorDocumento` (AC 23): campo de `ClienteContabilidade.cobranca?.pagadorDocumento`, já é o
  campo usado por `listarAlvosIss` para casar CNPJ/CPF (`iss-captura-repository.ts:42`).
- Sem alteração de RLS/rotas em `iss_execucoes_agente`/`iss_capturas` (0061) — permanecem como estão.
