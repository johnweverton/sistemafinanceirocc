# Story 3.2 — Emissão: payload completo do Cora + guard de cobrança

## Status
Ready for Review

## Story
**As a** operador financeiro,
**I want** que a emissão de boleto envie ao Cora o pagador completo (endereço, e-mail, documento
CPF/CNPJ) e as condições comerciais (vencimento/multa/juros/desconto), falhando cedo se faltar dado,
**so that** o boleto seja aceito pelo Cora e nenhuma emissão parta com dados incompletos.

## Acceptance Criteria
1. `cora-gateway.ts` monta `customer` com `email`, `address` completo e `document.type` dinâmico
   (`CPF`|`CNPJ`) a partir de `dados.pagador`.
2. `payment_terms` deixa de ser fixo (+30d): `due_date` vem de `diasVencimento` resolvido; `fine`,
   `interest` e `discount` são incluídos quando as condições tiverem valor.
3. A rota `POST /api/boletos/emitir` carrega o **médico** do resultado (via `medico_id`) e resolve
   as condições efetivas (override do médico ?? default `config_cobranca`).
4. **Guard:** se `cobrancaCompleta(medico)` for `false`, a rota retorna `422 COBRANCA_INCOMPLETA`
   com a lista de campos faltantes — **antes** de chamar o gateway.
5. Ordem do fluxo: `auth → flag → status 'ok' → valor>0 → cobrança completa → idempotência →
   gateway → auditoria`.
6. `mock-gateway.ts` continua funcional (só ecoa) e os testes existentes seguem verdes.
7. Testes cobrem: payload Cora inclui address/email/type correto (PF e PJ); 422 quando cobrança
   incompleta; `payment_terms` com e sem multa/juros/desconto.

## Complexidade e Riscos
- **Complexidade:** M (~3 pontos). Lógica concentrada em 2 arquivos, testável com mocks.
- **Escopo OUT:** ligar a feature flag e o certificado mTLS (gates externos, PRD §10); UI (3.3).
- **Riscos:**
  - Unidades de `fine`/`interest`/`discount` do Cora não confirmadas. *Mitigação:* testes de
    shape agora + confirmar na ativação real (a flag segue `false`).
  - `resultado.medico_id` nulo (resultado órfão). *Mitigação:* AC/tasks já preveem 422 claro.
- **DoD:** AC 1-7 + testes verdes + File List completa.
