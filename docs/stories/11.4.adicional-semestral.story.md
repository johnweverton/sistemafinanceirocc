# Story 11.4 — Adicional semestral (boleto avulso)

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** gerar o boleto avulso do adicional semestral de um cliente contábil (ex.: Vital
Soluções, R$15.000 a cada 6 meses), separado do boleto mensal,
**so that** essa exceção pontual saia pelo mesmo pipeline de emissão, sem misturar o valor com o
boleto mensal normal do cliente.

## Contexto
Quarta sub-story da Epic 11, depende da 11.1/11.2/11.3 (todas `Done`). Confirmado pelo dono
(2026-07-24): o adicional é um **boleto separado**, com valor **exatamente** `adicionalValor` (sem
somar ao mensal). Reaproveita o mesmo pipeline que a 11.3 já integrou — o adicional é só uma 2ª
execução no ciclo, marcada com `eh_adicional = true` (decisão D4 do desenho arquitetural).

## Acceptance Criteria
1. **Migration:** `execucoes.eh_adicional boolean not null default false`. Default `false`
   preserva 100% o comportamento das execuções existentes (médico/empresa/cliente contábil
   mensal).
2. **Tipos:** `Execucao.ehAdicional?: boolean`.
3. **Orquestrador:** `iniciarExecucao` ganha `ehAdicional?: boolean` — válido **somente** com
   `clienteContabilidadeId` setado e `cliente.adicionalAtivo === true` (422 nos demais casos).
   `processarExecucaoClienteContabilidade`, quando `execucao.ehAdicional`, ignora
   `modoCobranca`/faturamento e aplica `aplicarRegraPreco({ forma: 'fixo', valorFixo:
   cliente.adicionalValor }, 0)` — mesmo mecanismo de cálculo, regra montada em memória (não
   persistida) porque o adicional não é uma "regra de preço" do cadastro, é um valor à parte.
4. **Zod:** `dispararExecucaoSchema` ganha `ehAdicional` (opcional); refine: só pode vir `true`
   junto com `clienteContabilidadeId`.
5. **UI:** em `GerarExecucao.tsx`, quando `cliente.adicionalAtivo`, mostra um toggle "Gerar o
   adicional semestral desta competência (R$ X) em vez do boleto mensal" — e um indicador textual
   se a competência atual bate o ciclo (`adicionalCompetenciaBase` + `adicionalIntervaloMeses`),
   pré-marcando o toggle nesse caso (só sugestão, operador confirma).
6. `npm run typecheck`, `lint`, `test` verdes; testes: orquestrador (adicional gera resultado com
   `adicionalValor`; rejeita `ehAdicional` sem `clienteContabilidadeId`; rejeita `ehAdicional` em
   cliente sem `adicionalAtivo`), função pura do indicador de ciclo (casos de borda de mês),
   componente.

## Complexidade e Riscos
- **Complexidade:** M — extensão pequena e isolada do mesmo pipeline já integrado na 11.3 (1
  coluna booleana + 1 branch de valor no orquestrador + Zod + UI).
- **Escopo OUT:** relatório consolidado por cliente (11.5).
- **Riscos:**
  - Não confundir "gerar adicional" com "gerar mensal" na mesma competência — são 2 execuções
    independentes (2 `execucao_resultados`, 2 boletos), cada uma com seu próprio disparo manual;
    não há geração automática de nenhuma das duas.
  - Indicador de ciclo é só sugestão de UI — nunca bloqueia nem gera nada sozinho (mesmo espírito
    de "nunca automatizar sem confirmação manual", já usado na emissão de boleto desde o Épico 6).
- **DoD:** AC 1–6 + testes verdes + File List completa.

## Dev Notes
- **Regra montada em memória, não persistida:** o adicional usa `aplicarRegraPreco({ forma:
  'fixo', valorFixo: cliente.adicionalValor }, 0)` diretamente no orquestrador — não grava uma
  `RegraPreco` no cadastro, porque o adicional não é a regra de cálculo do cliente, é um valor à
  parte que só existe nesta execução.
- **Nome do resultado sinalizado:** `"${cliente.nome} — Adicional semestral"` para diferenciar na
  listagem de execuções/boletos do boleto mensal normal do mesmo cliente.
- **Indicador de ciclo é só sugestão:** `cicloAdicionalVencendoNaCompetencia` (função pura,
  `apps/web/src/lib/adicional-semestral.ts`) só pré-marca o toggle — o operador confirma
  manualmente antes de gerar, mesmo princípio de "nunca automatizar sem confirmação" já usado na
  emissão de boleto desde o Épico 6.
- **Validação em 2 camadas:** `ADICIONAL_NAO_ATIVO` (cliente sem o campo ativado) e
  `ADICIONAL_SEM_CLIENTE` (tentativa de marcar adicional numa execução por médico/empresa) — Zod
  replica a 2ª como defesa em profundidade (mesmo padrão já usado para `empresaId`/
  `clienteContabilidadeId`).
- **Não criado ainda:** relatório consolidado por cliente (11.5) — que vai mostrar o histórico de
  execuções mensais E adicionais juntos, diferenciados por `eh_adicional`.
