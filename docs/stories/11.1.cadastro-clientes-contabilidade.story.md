# Story 11.1 — Cadastro de clientes contábeis

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** cadastrar clientes de contabilidade (empresas atendidas pelo escritório) com regime
tributário, modo de cobrança, regra de preço e dados de cobrança,
**so that** o sistema tenha a base necessária para lançar faturamento mensal (Story 11.2) e emitir
boletos (Story 11.3) para essa carteira, sem misturar esse domínio com o de agregação médica
(`empresas`, Épico 10.4).

## Contexto
Primeira das 5 sub-stories da Epic 11 (Emissão para clientes de contabilidade), desenhada em
`docs/architecture/feature-emissao-contabilidade.md` (validado pelo dono em 2026-07-24). Regras de
negócio confirmadas pelo dono:
- **`faixa_faturamento`** (maioria do Simples Nacional): boleto varia por faturamento mensal
  informado (< R$5.000 → R$250; ≥ R$5.000 → R$480,56) — cálculo entra na Story 11.2.
- **`fixo`** (Lucro Presumido + exceções do Simples Nacional): valor fixo por contrato, reajustado
  1x/ano (manual, ver D5 do documento de arquitetura).
- **Adicional semestral** (exceção, ex.: Vital Soluções): boleto avulso de R$15.000 a cada 6 meses
  — geração entra na Story 11.4; aqui só cadastramos os campos de configuração.

Esta sub-story **só cria o cadastro** — nenhum lançamento de faturamento, execução ou emissão
ainda (mesmo recorte que a Story 10.4a usou para `empresas`).

**Reuso deliberado** (não reinventar): `DadosCobranca`, `CondicoesCobranca`, `ContaEmissora` são
reaproveitados tal como estão. `RegraPreco`/`RegraPrecoForma` (Story 10.1/10.4b) ganham uma nova
forma `'faixa_faturamento'` — extensão aditiva, não quebra médico nem empresa.

## Acceptance Criteria

     null` e `valorAcimaLimiar: number | null` (o campo `limiar` já existente é reaproveitado como
     o corte de faturamento). Médico e `Empresa` (Épico 10.4) continuam funcionando sem alteração —
     campos novos são opcionais/nulos pra eles.
   - Nova interface `ClienteContabilidade` — `id`, `nome`, `regimeTributario: 'simples_nacional' |
     'lucro_presumido'`, `modoCobranca: 'faixa_faturamento' | 'fixo'`, `regraPreco: RegraPreco |
     null`, `cobranca: DadosCobranca | null`, `contaEmissora: ContaEmissora`, `condicoes:
     CondicoesCobranca | null`, `adicionalAtivo: boolean`, `adicionalValor: number | null`,
     `adicionalIntervaloMeses: number | null`, `adicionalCompetenciaBase: string | null`, `ativo`,
     `createdAt`, `updatedAt`.

2. **Migration:** tabela `clientes_contabilidade` (colunas achatadas, mesmo padrão de `empresas` —
   migration 0028 — para cobrança/condições/regra de preço, mais `regime_tributario`,
   `modo_cobranca`, `regra_preco_valor_abaixo_limiar`, `regra_preco_valor_acima_limiar`,
   `adicional_ativo`, `adicional_valor`, `adicional_intervalo_meses`,
   `adicional_competencia_base`); tabela `clientes_contabilidade_historico` (mesmo padrão de

   `valor_abaixo_limiar` + `valor_acima_limiar`); `adicional_ativo = true` exige
   `adicional_valor`/`adicional_intervalo_meses`/`adicional_competencia_base` preenchidos. CHECKs

   `regraPrecoFormaSchema` (medico-schema.ts) ganha `'faixa_faturamento'`; `regraPrecoSchema` ganha

6. **UI:** `ClienteContabilidadeForm.tsx` + `ClientesContabilidadeManager.tsx` (nova tela em

7. `npm run typecheck`, `lint`, `test` verdes; testes: Zod (composição do schema + coerência da

## Complexidade e Riscos
- **Complexidade:** M (~5–6 pontos) — replica o padrão já validado de `empresas` (10.4a) para uma
  entidade nova, mais um campo de regra de preço adicional (`faixa_faturamento`).
- **Escopo OUT:** lançamento de faturamento mensal e cálculo `faixa_faturamento` em execução
  (11.2); execução/emissão de boleto (11.3); geração do boleto avulso semestral (11.4); relatório
  histórico por cliente (11.5).
- **Riscos:**
  - Extensão de `RegraPreco`/`RegraPrecoForma` é um tipo compartilhado com médico (10.1) e
    `Empresa` (10.4) — garantir que os campos novos (`valorAbaixoLimiar`/`valorAcimaLimiar`) fiquem
    `null`/opcionais para as formas existentes, sem quebrar `aplicarRegraPreco` nem os testes já
    verdes dessas stories.
  - Não confundir `clientes_contabilidade` com `empresas` (Épico 10.4) — são domínios diferentes,
    sem relação de FK entre si (ver D1 do documento de arquitetura).
- **DoD:** AC 1–7 + testes verdes + File List completa.

## Dev Notes
- **Reuso concretizado:** `dadosCobrancaSchema`/`condicoesCobrancaSchema`/`regraPrecoSchema`/
  `contaEmissoraSchema` importados diretamente de `medico-schema.ts` (zero duplicação). Os mappers
  `toDadosCobranca`/`toCondicoes`/`toRegraPreco` (já generalizados na 10.4a) são reaproveitados sem
  alteração — `ClienteContabilidadeRow` estende as mesmas interfaces estruturais
  (`CobrancaRowFields`/`CondicoesRowFields`/`RegraPrecoRowFields`) que `EmpresaRow`.
- **Extensão de `RegraPreco`/`RegraPrecoForma`:** `valorAbaixoLimiar`/`valorAcimaLimiar` foram
  adicionados como campos **opcionais** (`?: number | null`), não obrigatórios — evita exigir os 2
  campos novos em todo literal `RegraPreco` já existente nas Stories 10.1/10.4b (médico e
  `empresas`), que continuam compilando e passando nos testes sem alteração. `limiar` foi
  reaproveitado como o corte de faturamento; um `.refine` no Zod garante que `base_excedente`
  (guias) continue exigindo `limiar` inteiro, enquanto `faixa_faturamento` (R$, com centavos)
  aceita decimal — mesma coluna física em tabelas diferentes (`integer` em medicos/empresas,
  `numeric(10,2)` em clientes_contabilidade).
- **`ClienteContabilidadeForm`:** a regra de preço não é de forma livre como em `EmpresaForm` — o
  `modoCobranca` (faixa_faturamento/fixo) determina a forma da regra automaticamente
  (`onModoChange`), simplificando a UI (sem checkbox "Configurar").
- **Bug pego no teste de componente (auto-review):** o texto explicativo do campo "Regime
  tributário" estava dentro do `<Field>` (portanto dentro do `<label>`), entrando no accessible
  name do `<select>` e colidindo com a busca por "Modo de cobrança" (a frase citava "modo de
  cobrança abaixo"). Corrigido movendo o texto para um `<p>` irmão, fora do `<label>`.
- **Não criado ainda:** bloqueio de exclusão por vínculo (não há FK pra cá nesta story), lançamento
  de faturamento (11.2), execução/emissão (11.3), geração do adicional semestral (11.4), relatório
  histórico (11.5). `aplicarRegraPreco` (engine) não foi alterado — a forma `faixa_faturamento` é
  cadastrável mas ainda não é calculada em execução (fica pra 11.2).
- **Nav:** entrada "Clientes Contábeis" adicionada à Sidebar, entre "Empresas" e "Execuções".
