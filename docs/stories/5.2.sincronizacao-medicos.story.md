# Story 5.2 — Sincronização de médicos com a origem + matching assistido (backend)

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** sincronizar o cadastro de médicos com a API do Sistema Web, vinculando cada médico da
origem ao cadastro local por `external_id` — com sugestões de pareamento que EU confirmo,
**so that** os médicos entram no sistema sem digitação manual e sem risco de vínculo errado
(o vínculo é permanente e contamina histórico/cobrança se errado).

## Acceptance Criteria
1. Tipo `Medico` (`packages/shared`): `cpf` passa a `string | null` e novo campo
   `externalId: string | null`. Consumidores ajustados (mappers, schemas, engine, UI compila).
2. `mappers.ts`/`medico-repository.ts`: `MedicoRow` += `external_id`; novos métodos
   `buscarPorExternalId`, `vincularExternalId(medicoId, externalId)` e
   `criarMedicoExterno({ externalId, nome, statusHapvida })` — este cria com `cpf: null`,
   `necessitaConfiguracao: true`, `fazOutrosHospitais: false` (arquitetura §3.6).
3. Derivação `production_type` → `statusHapvida` (decisão 10 do épico):
   `"Produção Credenciada"` → `credenciado`; `"Produção VH"` → `nao_credenciado`;
   valor desconhecido → cliente vai ao relatório como `naoSincronizavel` (nunca lança):
   médico **já vinculado** mantém o `statusHapvida` atual (só alerta); `criar-externo` responde
   **422** — NUNCA criar com `statusHapvida='nenhum'` + `fazOutrosHospitais=false`, pois o CHECK
   `combinacao_classe_valida` (migration 0001) proíbe essa combinação e o INSERT falharia.
4. Novo `apps/web/src/server/medico-sync.ts`:
   - `sincronizar()` chama `listarClientes()` (5.1) e classifica cada cliente da origem em:
     `jaVinculado` (atualiza nome/statusHapvida se mudou, registra em `medicos_historico`),
     `comSugestao` (similaridade de nome com médico local **sem** external_id), `semPar` ou
     `naoSincronizavel` (production_type desconhecido — AC 3);
   - similaridade: normalização (minúsculas, sem acentos, remove títulos "dr/dra/dr./dra.") +
     comparação por tokens; empate/ambíguo → vai para `comSugestao` com TODAS as candidatas;
   - **nenhum vínculo ou criação acontece dentro de `sincronizar()`** — só leitura + relatório.
5. Rotas (todas `requireRole(['admin'])`):
   - `POST /api/medicos/sincronizar` → executa `sincronizar()` e responde o relatório
     (`{ atualizados, comSugestao: [{clienteExterno, candidatas[]}], semPar: [clienteExterno] }`);
   - `POST /api/medicos/vincular` (`{ externalId, medicoId }`) → confirma par sugerido
     (falha 409 se `externalId` já vinculado ou médico já tem outro vínculo);
   - `POST /api/medicos/criar-externo` (`{ externalId }`) → cria médico novo via
     `criarMedicoExterno` (busca dados do cliente na origem; 409 se já vinculado).
6. Vínculo e criação registram entrada em `medicos_historico` (campo `external_id`, autor, motivo).
7. `npm run typecheck`, `lint` e `test` passam; suíte existente permanece verde.

## Complexidade e Riscos
- **Complexidade:** L (~5 pontos). O ripple de `cpf: string | null` atravessa tipos, schemas e UI.
- **Escopo OUT:** UI de sincronização/pendências (5.4), execução (5.5), CSV (inalterado — importação
  por CSV continua exigindo CPF).
- **Riscos:** (a) ripple do `cpf` nullable quebrar consumidores — *mitigação:* typecheck guia;
  engine usa `cpf ?? ''` no snapshot do resultado; (b) matching errado — *mitigação:* decisão 9,
  nada é vinculado sem confirmação humana; ambíguo nunca decide sozinho.
- **DoD:** AC 1-7 + testes verdes + File List completa.
