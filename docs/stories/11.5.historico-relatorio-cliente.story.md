# Story 11.5 — Histórico e relatório consolidado por cliente

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** ver, numa única tela por cliente contábil, o cadastro, o histórico de faturamento
mensal, as execuções/boletos emitidos ao longo do tempo e um aviso quando o reajuste anual está
atrasado,
**so that** eu tenha um acompanhamento completo (do lançamento à emissão) sem navegar entre telas
separadas, fechando o pedido original do dono ("ter uma parte onde a gente clique na empresa e
consiga ver dividido... tudo que foi emitido até agora").

## Contexto
Última sub-story da Epic 11, depende de 11.1/11.2/11.3/11.4 (todas `Done`). Puramente consolidação
de leitura — reaproveita os dados já existentes (cadastro, `clientes_contabilidade_faturamentos`,
`execucao_resultados` via `cliente_contabilidade_id`), sem tabela nova.

## Acceptance Criteria
1. **Tipos:** `ExecucaoHistoricoMedicoItem` (Story 8.5, reaproveitado tal como está — nenhum campo
   é específico de médico) ganha `ehAdicional?: boolean`, para diferenciar boleto mensal de
   adicional semestral na listagem.
2. **Repository:** `historicoResultadosPorClienteContabilidade(clienteId)` em
   `execucao-repository.ts` — mesmo padrão de `historicoResultadosPorMedico` (join
   `execucao_resultados` + `execucoes!inner`, ordenado por competência desc).
3. **Rota:** `GET /api/clientes-contabilidade/[id]/execucoes` — histórico de execuções/resultados
   do cliente.
4. **Função pura (`apps/web/src/lib/reajuste-anual.ts`):** `reajusteAnualPendente(historico,
   criadoEm, hoje)` — true quando a última alteração de `regraPreco` (ou o cadastro, se nunca
   alterada) tem 12 meses ou mais. Usada só para clientes `modoCobranca: 'fixo'` (reajuste manual,
   decisão D5 do desenho arquitetural — não automatiza, só avisa).
5. **UI:** nova página `/clientes-contabilidade/[id]` (detalhe consolidado) — dados cadastrais,
   aviso de reajuste pendente (quando aplicável), histórico de faturamento (reaproveita a consulta
   já usada em `LancamentoFaturamento`), histórico de execuções/boletos (competência, tipo
   mensal/adicional, status, valor). Link "Ver detalhes" a partir da tela de edição do cliente
   (`ClientesContabilidadeManager`).
6. `npm run typecheck`, `lint`, `test` verdes; testes: função pura (`reajusteAnualPendente` —
   nunca alterado vs. alterado recentemente vs. alterado há mais de 1 ano), repository, componente
   básico da página de detalhe.

## Dev Notes
- **Reuso concretizado:** `ExecucaoHistoricoMedicoItem`/`toExecucaoHistoricoMedicoItem`/
  `ExecucaoHistoricoMedicoItemRow` (Story 8.5) reaproveitados tal como estão — só ganharam
  `ehAdicional` (opcional, default `false`). `historicoResultadosPorClienteContabilidade` é o
  mesmo padrão de `historicoResultadosPorMedico`, filtrando por `cliente_contabilidade_id`.
- **Achado no reuso (auto-review):** o teste pré-existente `historicoResultadosPorMedico` fazia
  `toEqual` com o objeto completo — a extensão do mapper (novo campo `ehAdicional: false` sempre
  presente) quebraria esse teste por `toEqual` ser estrito. Corrigido incluindo o campo no
  `toEqual` esperado (não é regressão de comportamento, é o novo formato do tipo compartilhado).
- **Aviso de reajuste só para `modoCobranca: 'fixo'`:** clientes `faixa_faturamento` nunca
  precisam de reajuste manual (o valor já varia automaticamente pelo faturamento mensal) — a
  query de histórico de cadastro (`clientes_contabilidade_historico`) só é feita quando
  `modoCobranca === 'fixo'` (`enabled` do useQuery), evitando I/O desnecessário.
- **`reajusteAnualPendente` é função pura, sem I/O** — usa a data de criação do cadastro como
  fallback quando a regra nunca foi alterada (cliente recém-cadastrado não dispara aviso
  prematuro; só aos 12 meses).
- **Fecha o pedido original do dono** (2026-07-22, dictado por voz): "ter uma parte onde a gente
  clique na empresa... consiga ver dividido... tudo que foi emitido até agora" — a página de
  detalhe consolida cadastro + faturamento + execuções/boletos numa tela só.
