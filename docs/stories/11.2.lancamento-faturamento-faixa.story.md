# Story 11.2 — Lançamento de faturamento mensal e cálculo por faixa

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** lançar o faturamento mensal de um cliente contábil no modo `faixa_faturamento` e ver o
valor do boleto calculado automaticamente,
**so that** o valor cobrado siga a regra combinada (< R$5.000 → R$250; ≥ R$5.000 → R$480,56) sem
cálculo manual, com histórico auditável de todo faturamento informado.

## Contexto
Segunda sub-story da Epic 11 (`docs/architecture/feature-emissao-contabilidade.md`), depende da
11.1 (cadastro de clientes contábeis, `Done`). Esta story:
- Estende `aplicarRegraPreco` (Engine, extraída na Story 10.4b) com a forma `faixa_faturamento`
  (cadastrável desde a 11.1, mas ainda não calculada).
- Cria o histórico de faturamento mensal por cliente (`clientes_contabilidade_faturamentos`).
- Cria a rota e a tela de lançamento com preview do valor calculado antes de confirmar.

**Escopo OUT:** execução/emissão de boleto usando esse valor (Story 11.3 — esta story só calcula
e registra o faturamento/preview, não gera `execucao_resultados` nem boleto).

## Acceptance Criteria
1. **Engine:** `aplicarRegraPreco` (`apps/web/src/server/engine/regra-preco.ts`) ganha o branch
   `forma === 'faixa_faturamento'`: `faturamento >= regra.limiar ? regra.valorAcimaLimiar :
   regra.valorAbaixoLimiar`. Regra incompleta (`limiar`/`valorAbaixoLimiar`/`valorAcimaLimiar`
   ausentes) nunca chuta valor — alerta explícito, valor 0 (mesmo padrão das outras formas).
2. **Tipos (`packages/shared`):** `ClienteContabilidadeFaturamento` — `id`,
   `clienteContabilidadeId`, `competencia` (string `'YYYY-MM'`), `faturamento: number`,
   `informadoPor: string`, `informadoEm: string`.
3. **Migration:** tabela `clientes_contabilidade_faturamentos` — FK para `clientes_contabilidade`,
   `competencia text not null`, `faturamento numeric(12,2) not null`, `informado_por uuid not null
   references profiles(id)`, `informado_em timestamptz not null default now()`, `unique
   (cliente_contabilidade_id, competencia)` (não permite 2 lançamentos pra mesma competência — updates
   corrigem o valor existente, não duplicam).
3. **Zod:** `lancarFaturamentoSchema` — `competencia` (regex `YYYY-MM`), `faturamento` (`number,
   min 0`).
4. **Repository:** `cliente-contabilidade-faturamento-repository.ts` — `lancarFaturamento`
   (upsert por `cliente_contabilidade_id` + `competencia`), `listarFaturamentos(clienteId)`,
   `buscarFaturamento(clienteId, competencia)`.
5. **Rotas:** `POST /api/clientes-contabilidade/[id]/faturamentos` (lança/atualiza o faturamento
   da competência, `requireRole(['admin','colaborador','financeiro'])` — lançamento mensal não é
   uma alteração de cadastro, não exige perfil admin), `GET
   /api/clientes-contabilidade/[id]/faturamentos` (histórico).
6. **UI:** nova página `/clientes-contabilidade/[id]/faturamento` — formulário de competência +
   faturamento com preview do valor calculado (chama a mesma lógica de `aplicarRegraPreco` no
   cliente, ou exibe o resultado devolvido pela API) antes de confirmar; lista os lançamentos
   anteriores da competência mais recente para a mais antiga. Link "Lançar faturamento" a partir
   da tela de edição do cliente (`ClientesContabilidadeManager`), visível só quando `modoCobranca
   === 'faixa_faturamento'`.
7. `npm run typecheck`, `lint`, `test` verdes; testes: engine (`aplicarRegraPreco` forma
   `faixa_faturamento` — casos abaixo/igual/acima do limiar, regra incompleta), Zod, repository
   (upsert idempotente por competência), componente básico da tela de lançamento.

## Complexidade e Riscos
- **Complexidade:** M (~4–5 pontos) — extensão pequena e isolada do Engine + 1 tabela nova + CRUD
  simples de lançamento (sem execução ainda).
- **Escopo OUT:** execução/emissão de boleto (11.3); adicional semestral (11.4); relatório
  consolidado por cliente (11.5).
- **Riscos:**
  - Igual ao limiar (R$5.000,00 exato) entra na faixa **acima** — confirmado pelo dono
    (2026-07-24): `faturamento >= limiar`. Cobrir esse caso de borda explicitamente no teste.
  - Lançamento em duplicata pra mesma competência deve **atualizar**, não criar um segundo
    registro — `unique (cliente_contabilidade_id, competencia)` + upsert garante isso.
- **DoD:** AC 1–7 + testes verdes + File List completa.

## Dev Notes
- **Reuso concretizado:** `aplicarRegraPreco` (Engine, `regra-preco.ts`) ganhou o branch
  `faixa_faturamento` no MESMO arquivo/função das Stories 10.1/10.4b — nenhuma lógica de cálculo
  duplicada. Parâmetro renomeado de `guias` para `quantidade` (só nome, sem mudança de assinatura
  posicional) para refletir que agora representa guias OU faturamento em R$, conforme o chamador.
- **Preview sem duplicar regra:** a rota `POST .../faturamentos` chama `aplicarRegraPreco` no
  servidor e devolve `{ faturamento, preview }` — a UI só exibe o resultado, não reimplementa a
  regra `< limiar`/`>= limiar` em JavaScript do cliente.
- **Upsert por competência:** `lancarFaturamento` usa `.upsert(..., { onConflict:
  'cliente_contabilidade_id,competencia' })`, espelhando a constraint UNIQUE da migration 0031 —
  relançar a mesma competência corrige o valor em vez de duplicar linha.
- **Sem histórico por campo:** diferente do cadastro (11.1), o lançamento de faturamento não usa
  o padrão `*_historico` — o próprio registro por competência (com `informado_por`/`informado_em`)
  já é a trilha de auditoria; não haveria "campo alterado" útil numa tabela de fatos mensais.
- **Auth mais permissiva no lançamento:** `POST/GET .../faturamentos` aceitam
  `admin`/`colaborador`/`financeiro` (não só admin) — lançar o faturamento do mês é operação de
  rotina, diferente de alterar o cadastro do cliente (que segue exigindo admin).
- **Não criado ainda:** geração de `execucao_resultados`/boleto a partir do faturamento lançado —
  isso é a Story 11.3. Esta story só calcula o preview e registra o histórico de faturamento.
