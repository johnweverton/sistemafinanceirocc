# Story 11.3 — Execução e emissão de boleto (mensal + fixo)

## Status
Done

## Story
**As a** operador do sistema de cobrança,
**I want** gerar a execução mensal de um cliente contábil (usando o faturamento já lançado, no
modo `faixa_faturamento`, ou o valor fixo do cadastro, no modo `fixo`) e emitir o boleto,
**so that** o boleto do cliente contábil saia pelo mesmo pipeline de emissão (Cora, idempotência,
feature flag, auditoria) já usado por médico e empresa, sem duplicar nenhuma dessas peças.

## Contexto
Terceira sub-story da Epic 11, depende da 11.1 (cadastro, `Done`) e 11.2 (faturamento/cálculo,
`Done`). Estende o MESMO trio `execucoes → execucao_resultados → boletos` e o MESMO orquestrador
que a Story 10.4b/c já estendeu para `empresas` — reaproveitando gateway Cora, idempotência,
feature flag e o branch de resolução do pagador em `/api/boletos/emitir`.

**Diferença chave em relação a `empresa` (10.4b):** não há agregação de N médicos aqui — um
cliente contábil não tem "produção" nem "lotes". O orquestrador ganha um 3º caminho **sem
lotes**, ainda mais simples que o de empresa: busca o cliente (+ o faturamento lançado, se
`faixa_faturamento`), aplica `aplicarRegraPreco` (Story 11.2) uma vez, grava 1 resultado, conclui.

## Acceptance Criteria
1. **Migration:** `execucoes.cliente_contabilidade_id` (FK nullable) e
   `execucao_resultados.cliente_contabilidade_id` (FK nullable) — CHECK estendida para as 3 vias
   (`medico_id`/`empresa_id`/`cliente_contabilidade_id`: nunca dois setados ao mesmo tempo, mesmo
   espírito não-XOR-estrito da migration 0029, compatível com médico legado sem vínculo).
2. **Tipos:** `Execucao.clienteContabilidadeId?: string | null`,
   `ExecucaoResultado.clienteContabilidadeId?: string | null`.
3. **Orquestrador:** `processarProximoLote` ganha o branch `execucao.clienteContabilidadeId` (sem
   lotes, resolvido de uma vez, mesmo padrão do branch de empresa):
   - Modo `fixo`: usa `cliente.regraPreco.valorFixo` diretamente via `aplicarRegraPreco`.
   - Modo `faixa_faturamento`: busca o faturamento da competência (`buscarFaturamento`, Story
     11.2); se não houver lançamento, grava resultado com `status: 'alerta'` e mensagem clara
     ("faturamento não lançado") — nunca chuta valor.
   - Grava 1 `execucao_resultados` (`cliente_contabilidade_id` setado, `medico_id`/`empresa_id`
     null) via novo `gravarResultadoClienteContabilidade`.
4. **Validação (`iniciarExecucao`):** cliente contábil existe e está ativo — mesma defesa em
   profundidade já aplicada a `empresaId`.
5. **Zod (`dispararExecucaoSchema`):** ganha `clienteContabilidadeId` (opcional); `selecoes` passa
   a aceitar array vazio **somente** quando `clienteContabilidadeId` está setado (cliente contábil
   não tem médicos para selecionar); mutuamente exclusivo com `empresaId` (defesa em profundidade,
   espelhando a CHECK do banco).
6. **Emissão:** `/api/boletos/emitir/route.ts` ganha o 3º branch (`resultadoRow.cliente_contabilidade_id`)
   — busca `clientes_contabilidade` para montar o pagador, reaproveitando
   `cobrancaMinimaEmissao` por tipagem estrutural (zero mudança nessas funções).
7. **UI:** ação "Gerar execução e emitir boleto" a partir da tela de edição do cliente contábil
   (ambos os modos) — sem tela de seleção de médicos (não existe): confirma a competência (padrão:
   mês atual) e dispara. Acompanha o resultado reaproveitando o padrão de execução já existente
   (`useExecucaoRealtime`/polling) se aplicável, ou uma versão simplificada síncrona dado que o
   processamento não tem lotes.
8. `npm run typecheck`, `lint`, `test` verdes; testes: orquestrador (mock de deps — modo fixo,
   modo faixa com faturamento presente, modo faixa SEM faturamento → alerta, cliente inativo →
   erro), Zod, rota de emissão (branch cliente contábil), componente básico do disparo.

## Complexidade e Riscos
- **Complexidade:** L — toca o orquestrador de produção (mesmo componente crítico que 10.4b já
  estendeu) e o pipeline de emissão real (Cora). Superfície de mudança pequena por design (branch
  isolado, mesmo padrão do de empresa), mas a área é sensível — tratar com o mesmo cuidado
  (CHECK não-XOR, idempotência por `execucao_resultado_id`, nunca chutar valor).
- **Escopo OUT:** adicional semestral (11.4 — boleto avulso fora do ciclo mensal); relatório
  consolidado por cliente (11.5).
- **Riscos:**
  - CHECK a 3 vias em `execucao_resultados` precisa do mesmo cuidado que 10.4b teve com
    `medico_id` legado nullable — replicar "nunca dois setados", não XOR estrito.
  - Reaproveitar `aplicarRegraPreco` sem alteração — a Story 11.2 já cobriu os casos de borda do
    cálculo; esta story só integra, não recalcula.
  - Auth da UI de disparo: mesma auth de `/api/execucoes` (`admin`/`colaborador`).
- **DoD:** AC 1–8 + testes verdes + File List completa.

## Dev Notes
- **Reuso concretizado:** mesmo trio `execucoes → execucao_resultados → boletos`, mesmo gateway
  Cora, mesma idempotência (`buscarBoletoEmitido` por `execucao_resultado_id`), mesma feature
  flag, mesmo `aplicarRegraPreco` (Story 11.2) — nenhuma dessas peças foi duplicada ou alterada
  além da extensão pontual necessária (3º branch no `if/else if` de resolução do pagador).
- **Sem lotes, mais simples que `empresa` (10.4b):** `processarExecucaoClienteContabilidade` nem
  precisa buscar médicos/produção — só o cliente + (no modo `faixa_faturamento`) o faturamento já
  lançado. Único ponto de leitura de `execucao.clienteContabilidadeId` em todo o orquestrador,
  mesmo espírito do branch de empresa (zero risco de regressão ao fluxo por-médico).
- **`iniciarExecucao` com `clienteContabilidadeId`** retorna cedo (antes das validações de
  seleção, que não fazem sentido aqui) — `selecoes` sempre `[]` nesse caminho.
- **CHECK a 3 vias:** `chk_execucao_resultados_exclusao_mutua` substitui
  `chk_execucao_resultados_nao_ambos_medico_empresa` (mesmo padrão não-XOR-estrito da 0029,
  compatível com médico legado `medico_id`/`empresa_id`/`cliente_contabilidade_id` todos null).
- **UI sem seleção de médicos:** `GerarExecucao.tsx` é um fluxo dedicado (competência → disparar →
  acompanhar via `useExecucaoRealtime`, já existente e reaproveitado sem alteração → emitir) —
  não reaproveita `NovaExecucao.tsx` (que é inteiramente sobre seleção de médicos/produção, sem
  aplicação aqui).
- **Não criado ainda:** boleto avulso semestral (Story 11.4 — usa o mesmo pipeline, mas como uma
  2ª execução no ciclo, com `eh_adicional`); relatório consolidado por cliente (11.5).
