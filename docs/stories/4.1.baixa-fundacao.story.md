# Story 4.1 — Fundação: tipos, mappers e repositório da baixa de boletos

## Status
Ready for Review

## Story
**As a** desenvolvedor do sistema de cobrança,
**I want** os tipos de domínio, mappers e métodos de repositório para a baixa de boletos e o
registro de eventos de webhook,
**so that** as stories de gateway (4.2), webhook (4.3) e recebíveis (4.4) tenham um contrato único
e correto para ler/gravar baixa e eventos.

## Acceptance Criteria
1. `packages/shared` amplia `StatusBoleto` para `'emitido' | 'falha' | 'pago' | 'cancelado'` e o
   tipo `Boleto` ganha `vencimento: string | null`, `pagoEm: string | null`, `valorPago: number | null`.
2. Novo tipo `BoletoEvento` (id, boletoId, idExterno, eventoId, eventoTipo, statusReconsultado,
   payload, recebidoEm) em `packages/shared`.
3. `mappers.ts`: `BoletoRow` inclui as colunas novas (`vencimento`, `pago_em`, `valor_pago`,
   `atualizado_em`); `toBoleto` popula os campos novos; novo `toBoletoEvento`/`BoletoEventoRow`.
4. `boleto-repository` ganha: `registrarEvento(evento)` idempotente (dedupe por `evento_id`;
   conflito → retorna o existente sem erro), `registrarBaixa(idExterno, { status, pagoEm, valorPago })`
   (atualiza `boletos` por `id_externo`, seta `atualizado_em`), e `buscarBoletoPorIdExterno(idExterno)`.
5. `npm run typecheck`, `lint` e `test` passam; suíte existente permanece verde.

## Complexidade e Riscos
- **Complexidade:** M (~3 pontos). Fundação sem UI; contrato consumido por 4.2/4.3/4.4.
- **Escopo OUT:** gateway (4.2), webhook (4.3), recebíveis (4.4).
- **Riscos:** ampliar `StatusBoleto` pode afetar consumidores existentes (mapper/rota emissão) —
  *mitigação:* mudança aditiva (novos valores no union), verificar exhaustive switches.
- **DoD:** AC 1-5 + testes verdes + File List completa.
