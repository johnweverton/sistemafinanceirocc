# Story 4.3 — Webhook de baixa do Cora

## Status
Ready for Review

## Story
**As a** operador financeiro,
**I want** que o sistema receba o webhook do Cora e dê baixa automática no boleto (confirmando pela
reconsulta na Cora, não pelo corpo do webhook),
**so that** os recebíveis reflitam os pagamentos sem conciliação manual e sem risco de payload forjado.

## Acceptance Criteria
1. Rota `POST /api/webhooks/cora/[secret]` existe e é **pública** (sem sessão); `api/webhooks` é
   adicionado à exclusão do `matcher` do `middleware.ts` (como `api/health`).
2. O `secret` do path é comparado em **tempo constante** com `CORA_WEBHOOK_SECRET` (env). Mismatch → 401.
3. **Idempotência:** o evento é registrado em `boleto_eventos` via `registrarEvento` (dedupe por
   `evento_id`); evento já visto → retorna **200** sem reprocessar.
4. **Reconsulta:** o handler chama `gateway.consultarInvoice(idExterno)` e usa o **status/valor da
   reconsulta** (não do corpo). `paid` → baixa `status='pago'` + `pago_em` + `valor_pago`;
   `canceled` → `status='cancelado'`.
5. Baixa aplicada via `registrarBaixa(idExterno, ...)`. Evento sem boleto correspondente (órfão):
   loga em `boleto_eventos` (boleto_id null) e retorna **200**.
6. A rota **sempre responde 200** para o Cora (exceto 401 de secret inválido); erros internos são
   logados, não propagados.
7. Testes cobrem: secret inválido → 401; evento pago → baixa 'pago'; reentrega (mesmo evento_id) →
   não duplica; evento órfão → 200 sem baixa. `typecheck`, `lint`, `test` verdes.

## Complexidade e Riscos
- **Complexidade:** M (~3 pontos). Rota + orquestração de idempotência/reconsulta/baixa.
- **Escopo OUT:** registrar a URL no Cora (ação @devops); ligar emissão (flag).
- **Riscos:**
  - Formato do payload/evento do Cora não confirmado (campos `evento_id`, `id_externo`, tipo).
    *Mitigação:* parser tolerante isolado + testes; ajustar ao integrar de verdade.
  - Rota pública — superfície de ataque. *Mitigação:* secret constant-time + reconsulta (fonte da
    verdade) + nunca confiar no corpo + sempre 200 (não vaza informação).
- **DoD:** AC 1-7 + testes verdes + File List completa.

#### Evidência
- typecheck ✅ · lint ✅ · testes 120 ✅ (401; pago→baixa; dedupe; órfão). Rota lida independentemente.

#### Segurança (foco) — todos ✅
- **Constant-time** do secret (`timingSafeEqual` com guarda de comprimento); secret ausente/divergente
  → **401 fail-closed**.
- **Não confia no payload** — usa `consultarInvoice` (reconsulta) como fonte da verdade. ✅
- **Idempotência** via `registrarEvento`; **sempre 200** (exceto 401) → sem enumeração/retry storm. ✅
- Escrita só via service role; erro loga **mensagem** (não payload/PII) e responde 200. ✅
- Middleware: `api/webhooks` excluído do matcher (rota pública sem sessão) — correto e documentado. ✅

#### Achados
1. **[MEDIUM — resolver antes do go-live]** `extrairEvento` usa `eventoId = event_id ?? idempotency_key ?? b.id`
   e `idExterno = resource.id ?? invoice_id`. **Se o Cora não enviar um event id distinto** e cairmos no
   fallback `b.id` (= id da invoice), dois eventos diferentes da MESMA invoice (ex.: `paid` e depois
   `canceled`) compartilhariam o mesmo `eventoId` → o **segundo evento seria deduplicado e perdido**.
   *Impacto:* baixa de cancelamento após pagamento poderia não ser aplicada. *Mitigação:* confirmar o
   campo real de id-do-evento do Cora e **remover o fallback para `b.id`** (ou derivar chave composta
   `tipo+invoice+timestamp`) antes de ligar a emissão. Não bloqueia agora (emissão desligada, formato
   não confirmado), mas é **item obrigatório de pré-ativação**.
2. **[LOW]** `boleto_eventos.status_reconsultado` fica null (dedupe antes da reconsulta) — dev já
   documentou; auditoria completa é follow-up opcional.
3. **[LOW]** Idempotência inexistente quando `eventoId` é null (evento sempre reprocessa) — mitigado por
   `registrarBaixa` ser idempotente (mesmo status = inócuo); só gera chamadas extras à Cora.

#### Recomendação
Criar **checklist de pré-ativação do webhook** (com @architect/@devops) cobrindo os itens 1 e os
campos assumidos da 4.2, a ser satisfeita antes de `GATEWAY_EMISSAO_HABILITADA=true` + registro da URL no Cora.

**Veredito:** CONCERNS — seguro publicar (backend pronto, emissão off). Item MEDIUM (idempotência do
event id) é obrigatório antes do go-live, não para o merge.
