# Story 3.1 — Fundação: contratos de domínio, validação e persistência de cobrança

## Status
Ready for Review

## Story
**As a** desenvolvedor do sistema de cobrança,
**I want** os tipos de domínio, validação e a camada de persistência dos dados de cobrança e
condições comerciais,
**so that** as demais stories (emissão, UI, CSV) tenham um contrato único e correto para ler e
gravar esses dados.

## Acceptance Criteria
1. `packages/shared` expõe `PagadorTipo`, `DadosCobranca`, `CondicoesCobranca` e `ConfigCobranca`,
   e `Medico` ganha `cobranca?: DadosCobranca | null` + os overrides comerciais opcionais.
2. Helper puro `cobrancaCompleta(m: Medico): boolean` retorna `true` somente quando todos os
   campos obrigatórios de cobrança estão preenchidos (complemento é opcional).
3. `DadosEmissaoBoleto` é reescrito com o bloco `pagador` (nome, documento, tipo `'CPF'|'CNPJ'`,
   email, endereco) — `cpfMedico`/`nomeMedico` deixam de existir no contrato.
4. `mappers.ts`: `MedicoRow` inclui as colunas novas; `toMedico` popula `cobranca` (ou `null` se
   vazio) e os overrides; `medicoUpdateToRow` mapeia os campos novos camelCase→snake_case.
5. Existe repositório para ler `config_cobranca` (singleton) e resolver condições efetivas por
   médico (`override do médico ?? default global`).
6. Zod: `dadosCobrancaSchema` (tipo, documento 11/14 por tipo, email, cep 8 díg., uf nas 27,
   demais obrigatórios) acoplado como bloco **opcional** em `novoMedicoSchema`/`atualizarMedicoSchema`.
7. `npm run typecheck`, `npm run lint` e `npm test` passam; suíte existente (78) permanece verde.

## Dev Notes
**Pré-requisito:** migration `supabase/migrations/0006_dados_cobranca.sql` aplicada (colunas em
`medicos`: `pagador_tipo`, `pagador_documento`, `pagador_nome`, `email`, `cep`, `logradouro`,
`numero`, `complemento`, `bairro`, `cidade`, `uf`, `dias_vencimento`, `multa_percent`,
`juros_mes_percent`, `desconto_percent`, `desconto_dias`; tabela `config_cobranca`).

Contratos (da arquitetura §4):
```ts
export type PagadorTipo = 'PF' | 'PJ';
export interface DadosCobranca {
  pagadorTipo: PagadorTipo; pagadorDocumento: string; pagadorNome: string; email: string;
  cep: string; logradouro: string; numero: string; complemento: string | null;
  bairro: string; cidade: string; uf: string;
}
export interface CondicoesCobranca { // overrides no Medico (todos opcionais)
  diasVencimento?: number | null; multaPercent?: number | null; jurosMesPercent?: number | null;
  descontoPercent?: number | null; descontoDias?: number | null;
}
export interface ConfigCobranca { // defaults globais (config_cobranca)
  diasVencimento: number; multaPercent: number | null; jurosMesPercent: number | null;
  descontoPercent: number | null; descontoDias: number | null;
}
```
- `toMedico`: se **todas** as colunas obrigatórias de cobrança estiverem `null`, retornar
  `cobranca: null`; senão montar o bloco (complemento pode ser `null`).
- `medicoUpdateToRow`: mapear cada campo novo (ex.: `pagadorTipo→pagador_tipo`,
  `email→email`, `diasVencimento→dias_vencimento`). Achatamento do bloco `cobranca` fica a
  critério do dev (pode receber campos achatados no payload de update).
- `medico-repository.ts` provavelmente já faz `select *` — confirmar que retorna as colunas novas.
- **Padrão do projeto:** único ponto que lê `process.env` é `lib/env.ts`; snake_case no banco,
  camelCase no domínio (ver `mappers.ts`).
